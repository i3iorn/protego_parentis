# Data safety form — answers

Every question on Play's Data safety form, with the answer and the code it comes
from. Fill the form from this file rather than from memory: the form is a legal
declaration, Play cross-checks it against what the app actually does, and a
mismatch is one of the commonest reasons a release is pulled after it has shipped.

Re-check this file whenever a new `SyncMessageType` is added. A new message type
that carries something about a person is a change to this form.

---

## The one thing that shapes every answer

**We operate no server and receive nothing.** There is no account, no back end of
ours, and no analytics. Data goes from one phone in a family to another, encrypted
on the sending device before it leaves.

Play's form still counts phone-to-phone traffic as **"data shared"**, because it
leaves the device and passes through a relay we do not control
(`https://ntfy.sh` by default — `SyncConfigStore.DEFAULT_SERVER`, changeable by
the user to any server including their own). Answer honestly: it is transferred.
Then use the free-text and the encryption-in-transit answers to say that the relay
receives ciphertext only.

Do not be tempted to answer "no data shared" on the grounds that it is encrypted.
It is transferred, and the encryption is a mitigation, not an exemption.

## Data collection and sharing

| Question | Answer |
|---|---|
| Does your app collect or share any of the required user data types? | **Yes** |
| Is all of the user data collected by your app encrypted in transit? | **Yes** — AES-256-GCM, key derived by PBKDF2 (210 000 iterations) from a family passphrase; see `MessageCrypto`. Messages are also signed with a per-device ECDSA P-256 key generated in the hardware keystore (`MessageSignatures`, `DeviceIdentity`). |
| Do you provide a way for users to request that their data be deleted? | **Yes** — in-app. Leaving a family (`FamilyData.forget`) erases everything received from other phones; clearing the conversation removes messages; uninstalling removes everything local. There is no account, so there is nothing server-side to request. |

## Data types — declare exactly these

### Location → Approximate location, Precise location
- **Collected:** Yes. **Shared:** Yes.
- **Purpose:** App functionality.
- **Required or optional:** **Optional.** The whole location feature can be turned
  off (`Feature.LOCATION`), and with it off the device does not answer a request
  at all — see `SyncCoordinator.applyLocateRequest`.
- **Processed ephemerally:** No (a parent's phone keeps the single most recent
  position until it is replaced or the family is left).
- **Notes for the free text:** sent only in response to an explicit request from a
  parent phone, or when the young person raises an emergency. The young person is
  notified every time, and each request is written to the shared history both
  sides can read. No trail: one position is held, with no history behind it
  (`FamilyEventStore.recordLocation`). Place arrivals send a place *name* and no
  coordinates (`PLACE_TRANSITION`).

### Personal info → Other personal info
- **Collected:** Yes. **Shared:** Yes. **Purpose:** App functionality. **Optional.**
- Covers the device name the user chooses, and free-text reasons typed when asking
  for more time.

### Messages → Other in-app messages
- **Collected:** Yes. **Shared:** Yes. **Purpose:** App functionality. **Optional**
  (`Feature.CHAT`).
- Text and emoji only. The app has no mechanism to send a picture, file or
  attachment — see `ChatText`. Kept on each phone, most recent 200
  (`ChatStore.MAX_MESSAGES`), clearable by either side.

### App activity → Other actions
- **Collected:** Yes. **Shared:** Yes. **Purpose:** App functionality. **Required**
  (this is the app's core function).
- Screen time per app and per day, which rules applied, requests and answers.
  What leaves the device is a daily summary: today's total, remaining allowance,
  and the five most-used apps with durations — no timestamps, no history
  (`DAILY_SUMMARY`).

### Web browsing → Web browsing history
- **Collected:** Yes. **Shared:** Yes. **Purpose:** App functionality. **Optional**
  and **off by default** (`WebFilterStore.countVisits`).
- Domain names looked up today and a count for each. No paths, no times of day, no
  page contents. Resets daily and no history is kept on either side
  (`WEB_SUMMARY`).
- Declare this one even though it is off by default and coarse. It is the answer
  most likely to be checked against the app's behaviour, and under-declaring it is
  the worst mistake available on this form.

### Device or other IDs
- **Collected:** Yes. **Shared:** Yes. **Purpose:** App functionality. **Required.**
- A per-device public key and its fingerprint, generated by the app. Not an
  advertising ID, not the hardware ID, and not linked to anything outside the
  family.

## Do NOT declare

These are worth listing so nobody adds them by mistake — none is collected and
none is accessible to the app:

Name · Email address · Phone number · Address · Financial info · Health · Photos ·
Videos · Audio · Files and docs · Calendar · Contacts · Call logs · SMS ·
Search history · Installed app *inventory sent off the device* (the list is read
on the device and never transmitted) · Crash logs · Diagnostics · Advertising ID ·
Purchase history.

The app's own diagnostic log (`Diagnostics`) never leaves the phone unless the
user chooses to share it themselves through the Android share sheet, so it is not
collected within the meaning of this form.
